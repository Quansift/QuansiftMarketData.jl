System Structure & Flow

Tiingo.jl データ基盤

Tiingo APIから正規化されたDataFrame、独立した3つの保存先、本番オーケストレーション、releaseとproduction deployまでを1枚にまとめた構造図です。

  • PostgreSQL = AUTHORITATIVE
  • DuckDB = OPTIONAL
  • Parquet = ARCHIVE

1. Collection → Normalization → Independent Sinks

  1. SOURCE

    Tiingo API

    Ticker universe、EOD、Daily Metrics。

  2. TIINGO.JL

    HTTP & Validation

    検証、上限付きretry、安全なエラー報告。

  3. TIINGO.JL

    Collectors

    collect_ticker_universe、collect_historical、collect_fundamentals。

  4. BOUNDARY

    Canonical DataFrames

    保存先に依存しない正規化データ。

↓ 用途に応じて独立に選択（複数選択可）

AUTHORITATIVE

System PostgreSQL

本番参照の正本かつ復旧基準。自然キーによる冪等upsert。

OPTIONAL

DuckDB

永続的な分析replica／高速OLAP cache。正本ではなく、保持期間はconsumerが決める。

ARCHIVE

Parquet

検証済みatomic local artifact。off-host公開後は全履歴archive／交換形式。

Package-only path: PostgreSQLの準備は不要です。Tiingo API keyからHTTP validation → collector → canonical DataFrameを経て、local DuckDBまたはParquetだけで収集・検証・分析できます。

2. Responsibility Boundary

Tiingo.jl owns

  • HTTP access、response validation
  • Ticker universe、EOD、Daily Metrics collection
  • Canonical DataFrame normalization
  • PostgreSQL、DuckDB、Parquet persistence primitives

quansift_scheduler owns

  • Cron、stage orchestration、cross-stage retry
  • Splitのdurable per-ticker retry queue
  • SpacesとManaged PostgreSQLへのpublication
  • QuantScreener／TATSU sequencing

3. Production Flow

  1. Schedule
    quansift_schedulerがstock、ETF、Fundamentals stageを起動。
  2. Collect & normalize
    Tiingo API → HTTP validation → collector → canonical DataFrameの境界を通過。
  3. Commit authoritative data
    System PostgreSQLへ冪等に書き込み、本番正本を更新。
  4. Materialize optional analysis state
    必要なconsumerだけがDuckDB replica／cacheを更新。
  5. Archive & publish
    Parquetを検証・atomic writeし、schedulerがSpacesへ全履歴を公開。
  6. Serve downstream
    Managed PostgreSQLへrolling 3年を公開し、QuantScreener／TATSUを順序制御。

Rolling 3年ルールはManaged PostgreSQL publicationだけに適用。System PostgreSQLとoff-host Parquetは全履歴を保持します。

4. Fundamentals Flow

  1. Tiingo APIからFundamentals metadataとDaily Metricsを取得・検証。
  2. collect_fundamentalsがsecurity observationsとfundamental daily metricsへ正規化。
  3. System PostgreSQLの2つのcanonical tableへ冪等upsert。
  4. 必要に応じてDuckDB analysis replicaまたはverified Parquet artifactへ独立に書き込み。

5. Split Recovery — Durable Per-Ticker Retry

  1. refresh前にtickerをschedulerのpending queueへ永続化。
  2. 対象tickerの全履歴をTiingo.jl collectorで再取得。
  3. ticker単位のPostgreSQL transactionで履歴を置換しcommit。
  4. Optional: DuckDBが構成されている場合だけanalysis replicaを更新。
  5. scheduler自身が、PostgreSQL commit後、かつDuckDB構成時はその更新完了後にpending entryを削除。

失敗時: transactionをrollbackし、エラーを記録してpending entryを残す。他tickerは継続し、次回runで再試行する。

6. PostgreSQL → Parquet Snapshot

  1. AUTHORITATIVE

    PostgreSQL table

    snapshot元。

  2. EPHEMERAL SCANNER

    In-memory DuckDB

    postgres extensionでscan。永続storeにはしない。

  3. ARCHIVE

    Verified Parquet

    temporary fileを検証後、local atomic publication。

postgres extensionはbuild時にinstallします。runtime library codeはLOADのみを行い、downloadしません。

7. PostgreSQL Schema Migration

  1. migrate_postgres!がmigration advisory lockを取得。
  2. tiingojulia_schema_migrationsから現在versionを確認。
  3. 順序付きschema変更とledger rowを1 transaction内で適用。
  4. 成功時にcanonical schema version 1をcommit。

migration error時はschema変更とledger更新をまとめてrollbackし、直前versionを正本として維持する。

8. Package Release ≠ Production Deployment

Public package release

  1. Feature branch
  2. Optional staging integration
  3. PR → main、required CI pass
  4. Exact release commitをmainへmerge
  5. Exact main SHAに対するstrict release preflight
  6. Registratorを起動
  7. General registry PRのmergeを待つ
  8. TagBotがimmutable version tagとGitHub Releaseを作成

Pre-registration中はmanual tagを作らず、competing version tagも許可しない。

Production deployment

  1. Tiingoとschedulerをmainで検証
  2. schedulerのTiingo SHA pinを一致させる
  3. Tiingo → schedulerの順でproductionをfast-forward
  4. cron停止・idle確認・git pull --ff-only
  5. migration／health／pin確認後にcron復帰
